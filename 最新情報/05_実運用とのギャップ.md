**11/21の追加合意**：[操作改善・ルーム編集・開設者の初回提案](10_操作改善とルーム編集_開設者の初回提案.md)を反映。主催者は投票前に4項目を編集でき、新規ルームは開設者の1品以上の公開後に参加者が追加する。既存ルームは開いたまま保持。提出は必要な下書きも同送し、最新状態を1回の通信で受け取る。DBは005も適用する。

初心者向け改訂：2026-11-21。「画面で最後まで進めること」と「実際の利用者へ安定して提供できること」の間に何が残るかを説明します。たとえば決定商品を保存できても、注文・支払い・配送が完了したことにはなりません。

## 具体例：主催者がCookieを消したら

ルームや決定は共通DBに残りますが、今のアプリは別端末やCookie紛失後の本人復元に対応していません。保存データが無事でも、操作する本人を確認する仕組みが不足することがあります。これが「機能は動くが、運用には残課題がある」という意味です。

以下の表は全部を今すぐ作るという指示ではありません。公開する前に必要なこと、実購入の前に必要なこと、利用状況を確かめてから追加を決めることを分けて使います。担当別の整理は[08](08_運用に向けたFront_Back_DBの作業.md)です。

現状はダミーデータを使う試作です。以下は「実装済み」ではなく、実運用に進める場合の検討・作業です。今回の開発範囲外である実決済・配送・本番公開を、この資料作成で追加実装していません。

## 優先して整理すること

HTTPSは画面やAPIとの通信を暗号化する方式、CORS・Originは別の住所からの通信をブラウザーやAPIが扱うときの設定、CSRFは別サイト経由で本人の意図しない操作をさせる攻撃への対策、監査は後から変更の経緯を確かめられる記録のことです。用語だけで完了と判断せず、表の「何を確認するか」を読んでください。

| 優先 | 残課題 | 現在の状態・必要な対応 |
|---|---|---|
| 公開前 | 公開先・接続先 | 現状は127.0.0.1。フロント／APIの共通URL、APIからDBへのIP許可、HTTPS、秘密の環境変数登録、DB適用手順が必要 |
| 公開前 | Cookie・CORS・Origin | 最新APIはlocal_roomsの許可先を再利用、CookieはHttpOnly・SameSite=Strict・Secure=Falseのローカル設定。公開ドメイン構成に合わせた安全なCookie属性と許可先、CSRF対策の設計・確認が必要。従来APIのCORS_ORIGINSだけでは足りない |
| 公開前 | 招待・閲覧範囲 | 名前参加＋数値ルームID。アカウント認証や秘密の招待トークンはない。ルーム基本情報取得と参加の公開範囲、荒らし・多重参加・推測アクセス対策を決める |
| 公開前 | 本人復元・主催者継承 | Cookie有効期限は30日。紛失・期限切れ・別端末での本人復元なし。主催者が操作不能な場合の復旧手段も必要 |
| 公開前 | 商品条件の確かさ | 送別タグ・価格・在庫・レビューは取得できるが、コメント中のアレルギー、日持ち、香り、配送日の適合を保証しない。商品属性の出典・更新と、人が確認する流れを決める |
| 実購入前 | 決済・注文・在庫予約 | payment=demoで決定保存するだけ。注文ID、決済状態、返金、在庫確保、価格変更対応、二重注文防止は未実装 |

| 継続運用前 | 個人情報・監査 | 内部ではmember_idを保存する匿名表示。コメントの健康情報等の扱い、削除依頼・保存期限・閲覧権限、主催者の差し替え履歴／理由の監査記録が必要 |

## 体験・業務ルールの残り

| 項目 | 現在できること | ギャップ・次に決めること |
|---|---|---|
| 全員の合意確認 | 匿名の★1〜3、評価人数、決定理由の公開 | 全員が読んだ／同意した記録なし。未投票でも主催者が決定可能。確認・反対・棄権・リマインド等は別途合意が必要 |
| 入室情報 | 3分類で任意投稿、収集期間に参照 | 入室フラグはブラウザー内state。再読込で再表示。コメントの編集・削除、重複制御は未実装 |
| 主催者の調整 | 他人の公開候補も差し替え・除外できる | 元下書きは残り、参加者の再提出で元候補が再登場し得る。禁止リスト・再登場防止・変更通知はない。主催者は投票直前の一覧を確認する |
| 期限 | 受取予定日の土日祝日をチェック | 提出／投票期限や締切通知はない。実際に届く日を計算せず、予定日を過ぎたルームの自動終了もない |

| 履歴 | 同じルームURLで商品・理由を再表示 | 全ルーム一覧、検索、会員への紐づけ、決定の取消・再決定はない |
| 理由の集計 | votes/comments/otherを固定コードで保存 | 集計API・画面・期間別分析・エクスポートはない。other自由文の集計方針も必要 |
| 旧実装の整理 | main/local/candidate_demo/singleを保持 | 最新と旧導線のAPI・制約が異なる。公開する入口の一本化、旧APIの公開停止／整理が必要 |
| 文書の統一 | 最新合意を正として要求・要件のmd本文を改訂。旧本文は履歴へ退避 | 原本Word／Googleドライブは未更新。チームで外部の正本にも反映する。対応は07参照 |

## テスト・検証の範囲

以前の作業記録には検索・参加・共有DB移行・共同決定のAPIテストと画面証拠があります。旧仕様の「5人×3品」のテスト実績を、新仕様の「全員・10品」の実績として数え直さないでください。

今回の最新修正に対する直前の実行結果は、通常Pythonテスト67件成功（別途19件の実DB用テストはskip）、実MySQLの追加シナリオ4件成功です。4件は主催者調整、上限での差し替え、コメント制御、複数選択理由の保存を確認したものです。実DB用19件すべてを最新修正後に再実行したという意味ではありません。

フロントの既存13件・lint・ビルドの成功実績はありますが、直近の商品レビュー表示の微修正後の最終ビルドは未完了です。11/21には学習用の架空ルーム34で、作成・主催者入室コメント・飲料のおまかせ・候補2品提出・投票開始・★3評価・理由3種類を付けた単品決定・再読込後の再表示を実画面で確認しました。[画面と図の記録](09_実画面とシーケンス図.md)を参照してください。これは1ブラウザーの確認であり、複数参加者の同時操作・カタログ決定を今回再検証したものではありません。自動テストは今回再実行していません。
