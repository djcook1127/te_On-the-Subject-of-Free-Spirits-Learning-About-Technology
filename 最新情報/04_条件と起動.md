# 機能条件・権限・開発時の接続

**11/21の追加合意**：[操作改善・ルーム編集・開設者の初回提案](10_操作改善とルーム編集_開設者の初回提案.md)を反映。主催者は投票前に4項目を編集でき、新規ルームは開設者の1品以上の公開後に参加者が追加する。既存ルームは開いたまま保持。提出は必要な下書きも同送し、最新状態を1回の通信で受け取る。DBは005も適用する。

初心者向け改訂：2026-11-21。前半は「誰が、いつ、何をできるか」、後半は「開発用アプリをどう動かすか」です。読むだけならコマンドを実行する必要はありません。DB準備は共有先の記録に影響するので、適用担当と対象を確認してから行います。

## 条件を3つに分けて読む

権限は「主催者だけか、全員か」、段階は「候補提出中か、投票中か、決定済みか」、入力条件は「10品以内か、文字数内か」などです。たとえば非主催者は候補提出中でも投票を開始できません。主催者でも投票開始後は候補を変更できません。

画面は操作できないボタンを無効にし、APIも同じ条件を確認します。ボタンの無効化だけでは、画面を使わない直接の依頼を止められないためです。

## 段階ごとの条件

| 操作 | collecting：候補提出期間 | voting：投票中 | decided：決定済み |
|---|---|---|---|
| 入室コメント | 全参加者。任意入力／スキップ | 投稿不可・一覧は閲覧可能 | 既存情報の参照のみ |
| 下書き保存・候補提出 | 開設者は最初から。参加者は開設者の最初の公開後 | 不可 | 不可 |
| 公開候補の追加・差し替え・除外 | 主催者 | 不可 | 不可 |
| 投票開始 | 主催者。候補1〜10品が必要 | 再開始不可 | 不可 |
| ★評価 | 不可 | 全参加者。1商品に1〜3、再評価で上書き | 不可 |
| ルーム情報編集 | 主催者のみ | 不可 | 不可 |
| 決定保存 | 不可 | 主催者 | 再確定・変更不可 |

ルーム作成で入力した人数は分担額計算の予定人数です。入室をその人数で制限したり、実際の人数に応じて自動で予算を変えたりはしません。提出期間は作成から手動の投票開始までで、期限の自動判定はありません。

## 上限・抽出・決定条件

| 項目 | 条件 |
|---|---|
| ルーム名・名前 | ルーム名1〜100字、ニックネーム1〜30字。前後空白除去。同一ルームの名前は一意 |
| 予算・予定人数 | 整数1〜2,147,483,647。負担額表示は総予算÷予定人数を切上げ |
| 受取期限 | YYYY-MM-DD。日本時間の今日以降、土日祝日不可。共通祝日データの対応は2026・2027年。配送可能日を保証する判定ではない |
| 提出 | 1人3品・提出者5人制限は撤廃。個人下書きは最大10品。提出時は全体で異なる商品ID最大10品。同じ商品は重複集計しない |
| 提案理由 | 商品ごと最大100字。相手についての入室コメントとは別 |
| コメント | 好み／避けたいもの／その他。本文1〜300字。入室時だけUI表示、API上の1人1回制限なし |
| おまかせ | 選択カテゴリー、送別タグ、在庫あり、価格が総予算80〜100％、商品レビュー平均4.0以上の全条件。異なる商品を最大3品ランダム表示 |
| おまかせ下限 | 円未満切上げ。`(budget*8+9)//10`。6,000円なら4,800〜6,000円 |
| カテゴリー | 上記条件を満たすDBのcategory値から取得。自由入力・固定の架空カテゴリーではない |
| 商品不足 | 少ない件数／0件をそのまま示す。条件を自動で緩めない。シャッフルでも同じ商品が出ることがある |
| 通常検索・お気に入り | おまかせ専用条件を一律には適用しない。提出時は存在・在庫、決定時はさらに予算内かを再確認 |
| 単品 | 公開候補から1品。最新価格が総予算以内、在庫あり |
| カタログ | 公開候補から重複なし1〜10品。受取人は1品選ぶ想定なので、各商品の価格が総予算以内か確認。掲載商品の価格合計を購入額としない |
| 決定理由 | votes／comments／otherから1〜3種類を重複なく複数選択。otherなら自由入力必須・最大300字。未選択時の自由入力はAPI拒否 |
| 合意 | ★投票や決定表示はあるが、全員同意・閲覧確認の証跡は記録しない |

## 起動入口を間違えない

このプロジェクトには開発途中のAPIが残っています。ファイルが存在するから全部同時に使うわけではありません。`selection_rooms:app`は「selection_rooms.pyの中のappというAPIアプリを動かす」という指定です。最新の共同決定を試すときはこれを選びます。

| API入口 | 用途 |
|---|---|
| `selection_rooms:app` | 今回の共同決定。ルーム保存先／商品取得元を別々に選択 |
| `main:app` | 従来の商品検索とルーム作成・取得。共同決定・名前参加の全APIはない |
| `local_rooms:app` | SQLite・固定商品で名前参加と旧個人入力 |
| `candidate_demo:app` | 旧固定参加者・候補入力のデモ |

| 変数 | 意味 |
|---|---|
| `GIFTIA_ROOM_STORAGE=shared` | 最新APIのルーム・候補等を共通MySQLへ保存。省略時はsqliteなので必ず明示 |
| `GIFTIA_CATALOG_SOURCE=shared` | 商品を共通DBから取得。省略時はdemo |
| `NEXT_PUBLIC_API_URL` | ブラウザーから到達するAPIのURL。秘密は置かない |
| `NEXT_PUBLIC_SELECTION_ROOMS=1` | 共同決定への導線とルーム作成時のCookie付き通信を有効にする |
| `GIFTIA_LOCAL_ROOMS_DB` | SQLite時の保存ファイル指定。未指定はリポジトリ内 `.local/room-preview.sqlite3`。過去に別ファイル指定で起動したものもある |
| DB接続変数 | DB_HOST・DB_PORT・DB_USER・DB_PASSWORD・DB_NAME・DB_SSL_CA。APIサーバー側に設定 |
| `CORS_ORIGINS` | 従来main:appで使う許可先。最新selection/sharedはlocal_rooms.ORIGINSを利用しており、この変数だけ変えても公開用許可先は切り替わらない |

共通DB障害時にSQLiteへ自動で逃がしません。503を返します。モードを変えると保存先・本人Cookieが別になります。

## メンバーのローカル起動例

11/21の操作確認ではビルド済み画面を`npm run start`で3300番に起動している。以下のdev手順へ切り替える場合は起動中の画面サーバーを止めてから行う。ビルドとdevを同時に同じ`.next`へ書き込ませない。ビルド済み画面へ変更を反映する場合は、API接続先と導線の環境変数を指定してbuildし直してからstartする。

「ローカル」は自分のPC内で動かすことです。画面とAPIは別のプログラムなので、ターミナルも2つ使います。3300や8102は同じPC内で行き先を区別するポート番号です。環境変数はコードと別に渡す設定で、画面の接続先とDBの接続先は別に用意します。

下記の`C:\path\to\existing\.env`等は例示のパスです。そのまま実行せず、自分の既存設定ファイルの場所へ置き換えます。設定の中身をチャットへ貼る必要はありません。

Python依存導入は `backend/requirements.txt`、Node依存は `frontend/package-lock.json` を使用。接続ファイルは各自が安全に管理し、コマンドの `/path/to/existing/.env` を自分の既存パスへ置き換えます。この資料に接続値は不要です。

Windows PowerShell（リポジトリ直下から、2つのターミナル）：

```powershell
cd backend
$env:GIFTIA_ROOM_STORAGE = 'shared'
$env:GIFTIA_CATALOG_SOURCE = 'shared'
python -m uvicorn selection_rooms:app --host 127.0.0.1 --port 8102 --env-file 'C:\path\to\existing\.env'
```

```powershell
cd frontend
$env:NEXT_PUBLIC_API_URL = 'http://127.0.0.1:8102'
$env:NEXT_PUBLIC_SELECTION_ROOMS = '1'
npm.cmd run dev -- --hostname 127.0.0.1 --port 3300
```

macOS（同じく2ターミナル）：

```sh
cd backend
GIFTIA_ROOM_STORAGE=shared GIFTIA_CATALOG_SOURCE=shared python3 -m uvicorn selection_rooms:app --host 127.0.0.1 --port 8102 --env-file '/path/to/existing/.env'
```

```sh
cd frontend
NEXT_PUBLIC_API_URL=http://127.0.0.1:8102 NEXT_PUBLIC_SELECTION_ROOMS=1 npm run dev -- --hostname 127.0.0.1 --port 3300
```

画面は `http://127.0.0.1:3300/`。localhostと127.0.0.1を混ぜず、同じホスト表記で利用してください。NextのNEXT_PUBLIC変数は本番ビルド時にも必要です。Azure側では実行するAPIの接続元IPが許可されている必要があります。接続ファイルの置き場所は自動的にどこでも検出されるわけではなく、上記の `--env-file` で明示します。

## DB準備・移行

起動はプログラムを動かすこと、DB準備は記録用の表や列を用意することです。コードを更新しても表が足りなければ保存できません。この表や列の変更をマイグレーションと呼びます。共通DBはみんなで同じものを使うため、各人が独自に作り直さず担当者が適用状況を管理します。

既存のconsultations・consultation_membersを活用します。新規DBでは `db/schema.sql` の基礎定義も必要です。既存共通DBには002→003→004→005の順で追加します。マージだけでDBスキーマは更新されません。

backendフォルダで、Windows：

```powershell
python manage_shared_storage.py --env-file 'C:\path\to\existing\.env' apply
python manage_shared_storage.py --env-file 'C:\path\to\existing\.env' apply-open-proposals
python manage_shared_storage.py --env-file 'C:\path\to\existing\.env' apply-entry-workflow
python manage_shared_storage.py --env-file 'C:\path\to\existing\.env' apply-organizer-first
```

macOSは同じ引数で `python` を `python3`、パスを `'/path/to/existing/.env'` に置き換えます。適用はDB単位。各メンバーの起動ごとには不要です。004の生SQLは重複列エラーになるため、再実行可能な管理スクリプトを使います。MySQL DDL全体を一括rollbackできるとは扱いません。

以前の作業で共通DBへ002・003・004を適用済みです。ただし今回は実DBの再照会を行っていません。旧SQLiteからのコピー手順と注意事項は [shared-storage.md](../docs/shared-storage.md) を参照。元ファイルを削除せずバックアップし、インポートは既存データを再同期する機能と混同しないでください。
