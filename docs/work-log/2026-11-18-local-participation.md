# 名前参加・個人候補入力と脆弱性修正の確認

Issue #21、統合PR #20。ユーザーが本チャットで「名前での参加から、商品候補・手掛かりの入力まで両方」「このローカル検証仕様で進める」と承認した範囲を実装した。

## 変更

- Next.jsとeslint-config-nextを16.4.2から16.4.6へ更新。`npm audit fix`で互換範囲の開発依存も更新した。
- `local_rooms:app`を追加。共通DB・環境ファイルを使わず、既存のローカルSQLiteでルーム作成・名前参加・本人別の個人候補入力を接続する。
- 作成者を参加済みとし、参加者はHttpOnly・SameSite=Strictのルーム別Cookieで再訪する。識別用の値はJSON・URLへ出さず、SQLiteにはハッシュだけ保存。既知の名前やIDを指定して他人の下書きを操作する機能は作らない。
- 同名重複・別名への変更を拒否。最大3枠・商品重複不可・空手掛かり不可・version競合の既存規則を維持。
- たけるさんの入力・日付規則を`room_contract.py`へ抽出してMySQL版と共有。既存候補検証も`prepare_slots`へ抽出して再利用。既存テストの期待値は変更せず、日付固定のモック対象だけ抽出後の場所に更新した。
- フロントはローカルルームで参加欄を表示し、既存の候補入力へ接続。固定架空参加者のデモやMySQL版はそのまま区別する。未保存でルームへ戻るときは確認を表示する。

APIテストでは、一時SQLiteで作成者の参加・名前参加・同名再送・重複と同時参加・本人再訪・期限切れ・別室Cookie拒否・他人IDの自己申告拒否・本人別下書き・商品情報の再取得・空保存・最大枠・同時保存競合・別Originの書込拒否・共通DB未接続を確認した。

脆弱性はGHSA-mfr8-8qww-v76h（Next.jsのキャッシュ情報漏えい）、および開発依存へ波及したGHSA-g3hv-75wg-m249（minimatchのDoS）の検出。以前の8件は依存経路上の件数を含む。今回の0件はnpmによる現時点の依存監査結果で、全ての安全性を保証するものではない。FastAPI TestClientの非推奨警告、Nodeのmodule形式の警告は残るが、今回の脆弱性検出とは区別する。

## 実画面で確認したこと

127.0.0.1:8300で`local_rooms:app`、127.0.0.1:3300で修正版の本番ビルドを起動。すべて架空データで、書込は`.local/room-preview.sqlite3`だけ。

1. ブラウザーで「参加・候補入力の確認ルーム」を作成。幹事として自動参加し、本人の候補入力へ移動。
2. コーヒーの商品を検索して追加、理由と手掛かりを入力して2枠保存。再読み込みで本人名・商品・理由・手掛かりを復元。
3. 別のAPIクライアントが作成した「名前参加の確認ルーム」を、Cookieを持たないブラウザーで開く。名前入力フォームを確認。
4. 「確認用の参加者」として参加し、本人の入力画面へ移動。手掛かりを保存し、再読み込みで復元。

画面証拠：

- [幹事の商品と手掛かり・再表示](evidence/2026-11-18-participation/organizer-draft.jpg)
- [名前参加後の本人の下書き・再表示](evidence/2026-11-18-participation/participant-draft.jpg)

旧版サーバーを止めている間の最初のブラウザー取得は接続拒否となった。修正版の起動後に再度開き、上記を確認した。画面幅はブラウザーの実際の表示幅を使用し、特定機種・全ブレークポイントの網羅テストは実施していない。同一ルームの本人間分離は独立CookieのAPIテストで検証し、実ブラウザーで複数ブラウザーを同時操作した確認とは区別する。

## 残件

共通MySQLへの参加・下書きの接続、本番の本人確認・権限、名前変更・Cookie喪失や別端末からの復元、正式提出・全員共有・推薦・投票は未実装。共通DBへのSQL適用・書込、実決済・本番公開は実施していない。元ブランチの公開済み秘密情報の解消は別対応。

起動と操作・識別の契約は[ローカル参加版](../local-participation.md)に記載。mainへのマージは行わず、PR #20でレビューする。
