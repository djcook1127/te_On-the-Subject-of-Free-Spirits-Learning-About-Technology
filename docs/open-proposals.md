## 流れ

1. 検索トップに、送別ルームの紹介と作成ボタンを表示。既存の検索欄・タブ・商品一覧とグローバルCSSは変更せず、追加バナーだけに独立したCSSを使う。
2. 名前で参加し、候補提出期間の入室時に相手について「好み／避けたいもの／その他」から選んでコメントする。情報がなければコメントせず入室できる。本人談か推測かも添える。
3. 全参加者が検索・お気に入り・おまかせから匿名で提出する。1人3品の制限は設けず、ルーム全体で異なる商品IDを最大10品にする。各人の編集中の下書きは本人だけに表示し、提出後に全員へ公開。同じ商品は1品にまとめ、理由は重複を除いて共有する。
4. 主催者は入室コメントを確認し、投票用の商品を追加・差し替え・除外できる。他の人の候補も調整可能。元の下書きは削除しない。主催者が調整した候補は、本人の通常の下書き再提出だけで消えないようにする。
5. 主催者だけが「投票開始」を押せる。未提出の人がいても開始でき、全員の自動提出待ちはしない。開始後は候補の変更とコメント投稿を止める。投票画面には常設相談欄やコメント入力を表示しない。
6. 全参加者が各候補に★1〜3を付けられる。未評価を同意とみなさず、同じ人の再評価は上書きする。
7. 主催者が1品または受取人が1品選ぶカタログを選び、決定理由を付けてデモの購入確認から保存する。参加者も商品と理由を確認できる。

「提出期間」は開始日・締切日の新設ではなく、ルーム作成から主催者の投票開始操作までの段階を指す。提出者名・コメント投稿者名・評価者名は共有表示に出さない。個人を識別するIDは内部で所属・権限・重複操作防止に利用する。

## おまかせ

以下をすべて満たす商品を、重複なく最大3品ランダム表示する。

- 利用者が選んだ、DBに存在するカテゴリー
- `product_scenes`の送別タグ
- 在庫あり
- 商品価格が総予算の80〜100％。下限は円単位で切り上げ（`(総予算×8+9)//10`）。6,000円なら4,800〜6,000円
- 商品レビュー平均★4.0以上。参加者の★1〜3投票とは別

カテゴリー一覧もこの条件を満たす商品のDB値から取得する。商品数不足や0件でも条件を自動で緩めない。既に自分の下書きで選んだ商品を除外する。同じ条件で再抽出するシャッフルのため、候補群が少なければ同じ商品が出ることがある。好み・アレルギー・お届け日の適合保証はしない。

検索・お気に入りからの通常提案は従来どおり。最終決定では最新の商品・在庫・総予算内かを確認する。お気に入りが空の場合は「会員登録がお済みでない方へ／新規登録をご検討ください」の案内を表示。会員状態の判定・登録ページ・認証・会員単位のお気に入り保存は今回作らない。お気に入りは引き続きブラウザー保存。

## コメントと既存情報

新しいコメントは入室時の分類付き入力へ集約する。画像で指摘された「贈る相手について、みんなで相談」の常設入力欄は削除。入室後は、候補提出期間に寄せられた内容を読む一覧だけを表示し、主催者が調整に使う。投票中はAPIでもコメント・共有情報を空配列にし、コメント・旧共有情報の追加入力を409で拒否する。

既存の`selection_notes`は分類付き情報として一覧へ残し、旧アレルギー・避けたいものの表示分類は「避けたいもの」にそろえる。旧商品コメントは元商品の文脈を添えて保持。これらの既存データを削除・書き換えない。新しい分類列追加前の自由コメントは「その他」として保持する。

## 決定理由の保存・表示

複数選択で、少なくとも1つ必須。

| 表示 | 保存コード |
|---|---|
| 投票結果を参考にした | `votes` |
| コメントを参考にした | `comments` |
| その他 | `other` |

「その他」を選んだときは最大300文字の自由入力を必須にし、その他未選択時の自由入力や重複選択はAPIで拒否する。決定JSONの`reasonSources`配列と`otherReason`に保存し、後からコードごとの件数を集計できる。商品・カタログと同じ決定履歴に参加者向けに表示する。以前の決定に理由がない場合は記録なしと表示し、理由を作らない。確認済み・同意済みの人数を新しく記録する機能は含まない。

## 保存と同時操作

- 個人下書き：既存`selection_proposals`。参加者全員の版番号は既存`selection_submitters`を利用し、5人制限は撤廃。
- 公開済み候補：追加`selection_published_proposals`。下書き保存中も以前の公開済み内容を維持。主催者調整は内部の`curated`列で保持し、共有APIにその出どころは返さない。
- 入室コメント：追加`selection_room_comments`の`kind`・`text`。
- ★評価・決定：既存`selection_votes`・`selection_state`。

MySQLではルームの親行ロック、SQLiteでは書込トランザクションで上限・段階・主催者権限を判定する。10品時も差し替えは原子的に行い、不正商品や失敗時は元の候補を保持する。他の参加者は提出期間中に再提出できるため、主催者は投票開始直前の一覧を確認する。開始後は追加・差し替え・除外をすべて拒否する。

## SQL適用・起動

既存共通DBには003の追加2テーブルと004の追加2列を適用する。既存のルーム・参加者・商品・コメント・決定履歴をDROPしない。初回の環境では002→003→004の順。API起動時にMySQLへDDLは流さない。適用スクリプトは既存の表・列を確認して再実行可能。SQL本体だけを直接再実行せずスクリプトを使う。

Windows（backend内）：

```powershell
python manage_shared_storage.py --env-file 'C:\Users\admin\OneDrive\Desktop\step3\backend\.env' apply-open-proposals
python manage_shared_storage.py --env-file 'C:\Users\admin\OneDrive\Desktop\step3\backend\.env' apply-entry-workflow
```

macOS（backend内）：

```sh
python3 manage_shared_storage.py --env-file '/path/to/existing/.env' apply-open-proposals
python3 manage_shared_storage.py --env-file '/path/to/existing/.env' apply-entry-workflow
```

起動は[共通DB保存手順](shared-storage.md)と同じ。`GIFTIA_ROOM_STORAGE=shared`、`GIFTIA_CATALOG_SOURCE=shared`。設定内容は表示・編集しない。実決済・配送・会員登録・外部公開・別端末の本人復元は今回の対象外。
