## 1. 目的・範囲

職場の送別で、相手の好みを詳しく知らない人が、参加者の情報・提案・評価を同じ場所で確認し、主催者が根拠を説明して決められる試作を作る。顧客の納得・全員の合意・購入率改善が実証されたという意味ではない。

今回の対象は検索トップからのルーム作成、名前参加、入室コメント、匿名提案、候補調整、匿名評価、単品／カタログの決定、理由付き履歴保存。実決済・集金・配送・受取人のカタログ引換・会員登録・本番公開は対象外。

## 2. 要求と実現範囲

| 要求ID | 顧客・事業の目的 | 今回の対応と限界 |
|---|---|---|
| BR-01 | 相手の好みが分からない中で、避けたいものや好みを判断材料に候補を検討する | 入室情報の共有、主催者調整、商品情報の比較。アレルギー適合・好みへの自動判定は保証しない |
| BR-02 | 選ぶ理由を共有し、一緒に贈る人が納得して決める | 匿名提案・投票、決定理由の複数選択と公開。全員の同意・既読を記録する機能はない |
| BR-03 | 比べられる数に絞る | 公開候補を異なる商品ID最大10品に制限。おまかせは最大3品表示。10品が最適かは未検証 |
| BR-04 | 納得を維持し、Giftiaでの購入につなげる | デモ決定までの行動を検証。実購入・実売上・購入率改善は測定済みではない |
| BR-05 | 予算・人数・受取期限等を確認して検討する | 条件入力、負担額表示、おまかせ価格条件、決定時の予算・在庫再確認。入り数や配送日による絞込は未実装 |

## 3. 機能要件と受入条件

既存IDは引き継ぐが、意味を変更した行は「変更」と明記する。未採用・延期は実装済みに数えない。新しい要件IDは今回追加した文書上の識別子。

| ID | 状態・機能 | 現行要件 | 対応BR | 受入条件 |
|---|---|---|---|---|
| FR-01 | 変更：ルーム作成 | ルーム名、総予算、予定人数、受取期限、主催者名を登録。主催者は投票前に4項目を編集可能。負担額は総予算÷予定人数の切上げ | 05 | 6000円・5人で1200円。作成と主催者登録は一体で保存。不正入力は保存しない |
| FR-02 | 変更：匿名提案 | 新規ルームは開設者が1品以上公開した後、参加者も検索・お気に入り・おまかせから提出。下書きは本人のみ、提出後は匿名で公開。ルーム全体で異なる商品最大10品 | 02・03 | 11品目は拒否。同じ商品は1品に統合。下書き編集中も以前の公開候補を維持 |
| FR-03 | 変更：おまかせ抽出 | 選択カテゴリー・送別タグ・在庫あり・価格が総予算80〜100％・レビュー平均4.0以上からランダム最大3品 | 03・05 | 6000円なら4800〜6000円。条件外は出さず、不足時も条件を緩めない |
| FR-04 | 旧ボット紹介を置換 | おまかせの条件とレビューを表示しシャッフル。通常検索は従来の販売数順、公開候補は合計星数降順・同点は商品ID順 | 03 | 関連度スコア・好き嫌い加減点・上位5件の紹介を行わない |
| FR-05 | 変更：候補比較 | 候補カードで商品名、カテゴリー、価格、レビュー、提案理由、投票値等を確認 | 03 | 公開候補を同じ項目で確認可能。香り・配送日等の不明属性を作らない。旧横並び表は今回対象外 |
| FR-06 | 変更：理由共有 | 参加者の提案理由と主催者の決定理由を共有。DBにない推薦根拠を自動生成しない | 01・02 | 提案理由は最大100字。自動推薦文章や関連度説明は出さない |
| FR-07 | 旧決定期限を延期 | 現行は受取期限入力のみ。候補提出期間は主催者の投票開始まで | 05 | 提出・投票の自動締切や決定期限入力を実装済みと扱わない |
| FR-08 | 変更：匿名評価・主催者決定 | voting中に全員が各商品へ★1〜3。再評価は上書き。主催者が集計を参考に商品を選ぶ | 02・03 | 1人の再評価で人数は増えない。最多票を自動決定しない。全員投票完了を必須としない |
| FR-09 | 変更：入室コメント | collectingの入室時に好み／避けたいもの／その他の任意コメント。投稿者名を出さずルームで共有 | 01・02 | 最大300字。スキップ可。常設入力・商品別コメントなし。voting中は投稿拒否。コメント一覧は評価中・決定時も匿名で閲覧可能 |
| FR-10 | 延期：チャット | 常設チャットは今回実装しない | 02 | コメントとチャットを同じ実装として数えない |
| FR-11 | 縮小：既存検索維持 | 従来のキーワード・カテゴリー・個包装・価格帯検索。検索トップにルーム紹介を追加 | 05 | バナー以外の既存検索の見た目・動作を維持。関係性・NG等の新しい贈答検索は未実装 |
| FR-12 | 延期：配れる人数 | 入り数による商品絞込は今回実装しない | 05 | 予定参加人数による負担額計算と混同しない |
| FR-13 | 延期：配送日絞込 | 受取期限の入力チェックのみ。配送・発送日数による候補除外はしない | 05 | 土日祝日拒否を、到着保証の実装と扱わない |
| FR-14 | 変更：贈り方 | 集計時に主催者が単品／受取人が1品選ぶカタログを選択 | 01・02 | 入口では選ばない。単品は1品、カタログは重複なし1〜10品 |
| FR-15 | 変更：相手の共有情報 | FR-09の3分類コメントへ集約。出どころは自由文で補足可能、専用列・自動除外はない | 01 | 旧like/dislike/owned/ng構造や本人談等の構造化選択を現行として要求しない |
| FR-16 | 変更：カタログ保存 | 主催者が公開候補から掲載商品を選び、各商品が総予算以内か確認して保存 | 01・02 | 受取人は1品選ぶ想定。価格合計を購入額としない。受取人専用画面・引換は未実装 |
| FR-17 | 追加：名前参加 | 招待URLからニックネーム登録、Cookieで本人照合。作成者を主催者登録 | 02 | 同一ルームの名前は一意。Cookieなしは未参加。別端末の本人復元なし |
| FR-18 | 追加：候補調整・投票開始 | collecting中に主催者が他人の公開候補も追加・差し替え・除外。手動でvotingへ変更 | 01・02・03 | 候補1〜10品で開始。開始後は候補変更不可。失敗した差し替えで元候補を失わない |
| FR-19 | 追加：決定理由・再閲覧 | votes/comments/otherから1つ以上を複数選択し、商品・贈り方と保存。参加者が同じURLで閲覧 | 02 | otherは最大300字の自由入力必須。重複コードを拒否。決定後は変更不可 |
| FR-20 | 追加：お気に入り案内 | ブラウザー保存の商品を候補選択に利用。空なら未登録者向けの新規登録案内文を表示 | 03 | 登録ページ・会員判定・会員DB保存は実装しない |

## 4. 利用フロー・画面・API

ルーム作成→入室→商品候補・諸情報登録→主催者調整→投票→集計・デモ決定→再閲覧。

| 画面URL | 担当 | 内容 |
|---|---|---|
| `/` | frontend/app/page.tsx | 既存検索と送別ルーム紹介 |
| `/rooms/new` | frontend/app/rooms/new/page.tsx | 作成フォーム |
| `/rooms/[roomId]` | frontend/app/rooms/[roomId]/page.tsx | 予算・予定人数・受取期限・招待URL・共同決定へのリンク |
| `/rooms/[roomId]/select` | select/page.tsx → SelectionWorkspace.tsx | 名前参加・入室コメント・提案・投票・集計・デモ確認・決定表示を画面内で切替 |
| `/favorites/farewell` | frontend/app/favorites/farewell/page.tsx | ブラウザー内お気に入り |

`/search`・`/compare`・`/profile`・`/catalog/pick`等の旧画面案は現行ルートとしない。旧`/single`系は検証用に残るが、最新の共同決定の入口ではない。詳細な呼出順は[機能とファイル](../最新情報/03_機能とファイル.md)。

APIの基点は `selection_rooms:app`。以下の`S`は `/api/rooms/{room_id}/selection` の略。Cookie付き通信で所属・権限を確認する。

| メソッド・パス | 役割・主な入力 |
|---|---|
| GET `/api/search` | 従来条件による商品検索 |
| POST `/api/rooms` | title・budget_total・member_count・deliver_by・nicknameで作成 |
| GET `/api/rooms/{room_id}` | ルーム基本情報 |
| GET `/api/rooms/{room_id}/me` | Cookieに対応する本人 |
| POST `/api/rooms/{room_id}/members` | nicknameで名前参加 |
| POST `/api/rooms/{room_id}/migrate-session` | 旧Cookieの明示引継ぎ |
| GET `S` | 本人下書き・公開候補・評価集計・段階・決定 |
| PUT `S/room` | title・budget_total・member_count・deliver_byを主催者が投票前に編集 |
| PUT `S/proposal` | version・productsで下書き更新 |
| POST `S/submit` | 保存済み下書きを公開。任意でProposal本文を同送し、一体保存・最新selectionを応答 |
| GET `S/categories` | おまかせ条件に合うカテゴリー |
| GET `S/random` | category必須、exclude任意。最大3品 |
| POST `S/comments` | kind・text。collectingのみ |
| POST `S/curation` | productId・replaceProductId任意・reason任意。主催者のみ |
| POST `S/curation/remove` | productId。主催者のみ |
| POST `S/start-voting` | 主催者のみ、collecting→voting |
| PUT `S/products/{product_id}/vote` | stars整数1〜3。votingのみ |
| POST `S/decision` | mode・productIds・reasonSources・otherReason。主催者、votingのみ |

互換APIの`S/notes`は旧情報登録用に残るが新UIでは使用しない。`PUT S/submitters`は410（指定提出者制度廃止）。旧案のrecommendations・purchase-clicks・messages・profile・catalog-picks等を実装済みAPIとして記載しない。

## 5. データ要件・保存設計

| ID | 状態・内容 | 対応BR |
|---|---|---|
| DR-01 | 旧贈答属性の新規整備は延期。既存products・product_scenesを読む。香り等の新しい属性表は今回追加しない | 01 |
| DR-02 | ルーム・参加者・本人セッション・下書き・公開候補・コメント・評価・段階を共通MySQLへ保存 | 02・04・05 |
| DR-03 | 購入遷移イベント計測は未実装。デモの決定保存を実購入・クリックログと扱わない | 04 |
| DR-04 | 贈り方・決定商品控え・複数選択理由をselection_state.decision JSONへ保存。同じルームから再取得 | 01・02・04 |

既存`consultations`・`consultation_members`を再利用。002で8表、003で公開候補と入室コメントの2表、004でkind・curatedの2列、005でorganizer_submittedを追加。新規行は0、既存行は1で開始。ER図・列・主キーと注意点は[接続とデータ](../最新情報/02_接続とデータの流れ.md)、適用順は[起動手順](../最新情報/04_条件と起動.md)。DDLはAPI起動時に自動適用しない。

旧案のproduct_gift_attributes・consultation_posts・consultation_profiles・catalog_picksを、今回実装した保存先とは扱わない。旧selection_notes・selection_commentsは既存情報を残す。お気に入りは共通DBではなくlocalStorage。

MySQLは親ルーム行ロック、下書きはversion、一連の書込はトランザクションで制御。候補・決定に商品JSONの控えを持つ。商品IDの実在はAPI確認であり、productsへの外部キーは新設しない。商品確認用の別接続は在庫予約ではない。

## 6. 検索・抽出・並び順

- 通常検索：在庫あり、キーワード・カテゴリー・個包装・価格等の既存条件。販売数降順、同点は商品ID順。
- おまかせ：FR-03の全条件。価格下限は`(budget*8+9)//10`。自分の下書き商品を除外し、ランダム最大3品。条件を緩めない。少数ならシャッフルしても再登場する。
- 公開候補：商品IDで重複をまとめ、合計星数降順、同点は商品ID順。商品レビューと参加者評価を混同しない。
- 旧関連度スコア、好き嫌いの加減点、自動NG除外、LLM推薦、ボットの上位5件紹介は今回の要件から外す。必須処理への適合は運営の元資料との再確認が必要で、今回その適合を新たに保証しない。

## 7. 非機能要件・条件

| ID | 現行要件・限界 |
|---|---|
| NFR-01 | DBの秘密はサーバー側設定、Git・ブラウザーに載せない。SQLの値をパラメーターで渡す。名前参加は会員認証の代替実装であり、本格認証ではない |
| NFR-02 | 共有表示は提案者・評価者・コメント投稿者を匿名にするが、DBはmember_idを保持。入力文に個人情報が入り得るため「個人情報なし」と断言しない。受取人画面は未実装で、そちらの閲覧権限確認を済んだものとしない |
| NFR-03（追加） | 権限・段階・上限をAPIで検証。失敗はrollback。MySQL障害時は503で、SQLiteへ自動退避しない |
| NFR-04（追加） | 移行はバックアップ・新ID対応・二重コピー防止。既存データのDROPや再同期はしない |
| NFR-05（追加） | 快適性を優先し、検索中の商品追加を妨げない。表示済み商品追加は通信なし。投票は保存中の仮表示と失敗時の復元。各保存APIは最新状態も返し追加GETを省く。初回接続・保存完了の待ちを別々に測定する |

受取期限は日本時間の今日以降、土日祝日不可、2026・2027年の祝日データ範囲。ルーム名1〜100字、名前1〜30字、予算・予定人数は正の整数。詳細は[条件一覧](../最新情報/04_条件と起動.md)。

構成はNext.js→FastAPI→Azure MySQL。ローカル設定のCookie・Origin許可を利用しており、本番のHTTPS・CORS・本人復元・監視等は残課題。応答2秒以内や総費用0円は達成確認済み要件として扱わない。性能目標と計測条件・基盤費用は別途定義する。

## 8. 検証と未解決事項

受入条件は3章を使う。テスト実績は作業記録および[残課題](../最新情報/05_実運用とのギャップ.md)を参照。仕様をそろえたことを、統合後の全テスト完了・顧客検証完了とは扱わない。

未解決：全員の合意・既読、提出／投票期限、公開環境、Cookie紛失時の復旧、受取人の引換、実注文、商品属性・配送日判定、購入イベント計測、理由集計画面、性能測定、旧導線整理。入室フラグは画面内stateなので再訪時に再表示、コメント1人1回制限なし。主催者が除外しても元下書きは残り、参加者の再提出で再登場する場合がある。
