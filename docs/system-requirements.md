## 2. 1〜3年後の姿と Phase1

| 1〜3年後の姿 | 複数人で贈るギフトを、情報集め→候補→決定→集金→配送までGiftia内で完結できる。決定と反応のデータで提案が改善していく |
| --- | --- |
| Phase1 でやること | 送別の共同購入に絞る。・相談ルーム（購入ルール・受け取り期限・期限・1人あたり負担額）・贈り方の選択・共有プロフィール・候補の投稿（1人3つ・理由・届く日の確認）・ボットの紹介と比較表・★による決定・作れたら：カタログギフト（受け取る人用はプレビューまで） |
| Phase1 でやらないことと理由 | ・ログイン：ニックネームと招待URLで代える（NFR-01）・決済・集金：負担額の表示まで・通知：画面表示で代える・同世代の分析：購入者の年代・反応データがない・本番公開（Exhibit 5） |
| Phase1 で検証すること（要求定義書 6章との対応） | 要求定義書6章の前段として確かめる。・サイト内で投稿から決定まで進めるか・決定後に購入ページへ進むか（DR-03）・決定までにかかる時間 |
| Phase2 以降 | 集金、通知、受け取る人の選択と配送、購入後アンケートによる推薦改善、LLMでの理由の文章化、他シーンへの展開 |

### 受け取り期限の入力仕様（2026-11-15決定）

- 「期日」「渡す日」「届けたい日」の入力・表示名は「受け取り期限」に統一する。DB・APIの項目名は既存案の`deliver_by`を維持する。
- 受け取り期限は、その日までに商品を受け取るための上限日を表す。到着日をその日に指定する意味ではない。
- カレンダーでは土曜日・日曜日・祝日を選択できない。
- 手入力やAPIへの直接送信でも、土日祝日の受け取り期限は受け付けず、理由を表示する。入力の検証は画面とAPIの両方で行う。
- 選択不可の日を自動的に前後の平日へ変更しない。利用者が選び直す。
- 決定期限は別項目として残す。今回の決定は決定期限の土日祝日を禁止する仕様ではない。
- 祝日は日本の国民の祝日・振替休日・国民の休日を含む（2026-11-15ユーザー承認）。祝日データは内閣府の公表済み2026・2027年分をshared/japan-holidays.jsonで共有する。他の年はデータ更新まで受け付けない。発送・配送日数から土日祝日を除く計算方法は別途確定する。
